# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm dev           # Start all apps in development mode (Turborepo)
pnpm build         # Build all apps and packages
pnpm lint          # Lint all packages
pnpm type-check    # TypeScript check across all packages
pnpm test          # Run all tests (Vitest, run-once)
pnpm test:watch    # Run tests in watch mode

# Run a single test file
pnpm vitest run apps/web/src/__tests__/calendar/EventDetail.test.tsx
```

## Architecture

**Monorepo layout** — Turborepo + pnpm workspaces.

```
apps/web/          # Next.js 15 app (App Router) — all user-facing routes
packages/
  api-*            # One thin API client per backend service (calendar, core, docs, etc.)
  ui/              # Shared component library (Button, Modal, Toast, Select, etc.)
  tokens/          # Design tokens (CSS variables, imported via packages/ui/src/styles/)
  layout/          # Shell components (Topbar, Sidebar) — moved out of @neutrino/ui
  hooks/           # Shared React hooks
  auth/            # Auth API client + useAuth hook
  e2e-crypto/      # End-to-end encryption helpers
  utils/           # Shared utilities
```

**App Router structure** — all user-facing routes live under `apps/web/src/app/(apps)/`. The `(apps)` route group shares a common shell layout (`layout.tsx`). Individual apps (calendar, docs, drive, notes, photos, sheets, slides, settings) each have their own route directory there.

**Page gutter and width** — `AppShell` gives its main area no padding: full-bleed routes (the docs/sheets/slides/drawing/photos editors, calendar, settings, admin, profile, import, users) fill it and draw their own chrome. Every other route composes the gutter in from `(apps)/pageContainer.module.css` — `composes: container from '…/pageContainer.module.css'` on its root rule — which is `padding: var(--space-6)` plus a `--page-max-width` (1200px by default) the page is centred within, so content does not hug the sidebar on a wide screen. Override the width by setting `--page-max-width` on the composing class, not a `max-width` declaration: both are single-class selectors, so a redeclaration is a specificity tie decided by stylesheet order. A new content page that forgets to compose it renders flush against the sidebar with no padding at all — that is issue #71, which the shell used to prevent by padding `.main-inner` until #41 removed it for the photo editor.

**Sidebar navigation** — the sections live in `apps/web/src/app/(apps)/navSections.ts`, not in `layout.tsx`, so they can be unit-tested (`src/__tests__/navSections.test.ts`) without rendering the shell. The first (unlabelled) section holds Drive views only; every application sits under the **Apps** header; then Team, per-tag entries (`lib/tagNav.ts`), and Administration for admins. `withActiveItem` marks the entry whose href is the longest prefix match for the current pathname, so `/docs/editor` keeps Docs highlighted while `/drive/trash` highlights Trash rather than My Drive. Adding an app means adding an entry here, a landing page, and a row in `e2e/tests/navigation/sidebar.spec.ts`.

**Office Suite landing pages** — `/docs`, `/sheets`, `/slides` and `/drawing` are thin wrappers over `apps/web/src/app/(apps)/DocumentLibrary.tsx`, which owns the whole listing experience: the `FileGrid`, create button, empty state, right-click menu (Preview / Rename / Copy link / Move to trash) and rename dialog. Each page supplies only its labels, icon, editor path, React Query key and four callbacks (`fetchItems`, `createItem`, `renameItem`, `deleteItem`); deletes go through `storageApi.deleteFile` for all of them since these are Drive files. `previewKind` is what `DocumentPreviewModal` renders — omit it (as `/drawing` does) and the Preview item disappears. `/notes`, `/photos` and `/diagrams` predate this component and still have hand-written pages.

**Drive views** — My Drive (`drive/page.tsx`), Recent, Starred, Shared with me, Trash, the tag pages **and a team's Files page** all render `FileGrid` from `@neutrino/ui`, which owns the Large grid / Small grid / Detailed list selector, the filter chips and the sort bar. `drive/gridItems.ts` holds the domain → `GridItem` mappings (`fileToGridItem`, `folderToGridItem`, `trashFileToGridItem`, `trashFolderToGridItem`, `teamFileToGridItem`, `teamFolderToGridItem`, `teamSharedFileToGridItem`) so every surface shows the same icon, subtitle and star state. A team's library is in that list because a team file *is* a Drive file — a `files` row scoped by `team_id` — and the hand-written list `teams/space/FilesView.tsx` used to draw was a second, poorer answer to a question Drive had already answered; two fields have no team answer and are left off rather than faked, since a star is a personal mark on a personal file and the library listing carries no thumbnail. Its chips filter client-side (the library endpoint takes no `?type=` and returns the folder in one response), and the files members have *lent* to the team stay in a second grid below the first, because a lent file is not in the library, does not count against the team's meter, and is somebody's to take back. My Drive sorts server-side via the query key; the other views have no sort parameters on their endpoints and sort client-side with `sortEntries`. The filter chips group by what a file *is* — Media, Office, Drawings, PDFs, Archives, Code, plus All and Starred — rather than by which app owns it, because the sidebar already has an entry per app; `categorizeMime` gives every file exactly one of them, so the chips partition the listing instead of overlapping it. The chip keys are the backend's own category names (`DriveFileType` in `src/drive/filesystem/dto.rs`), so My Drive owns the chip (`filter`/`onFilterChange`) and sends it as `?type=` on the folder endpoint, where it is answered in SQL and each chip pages through its own listing. The one key that is not the label is `canvas` (labelled "Drawings", holding diagrams *and* drawings) — the backend's `drawing` is the drawing app alone, and per-app types are pinned by shipped iOS builds and cannot be re-scoped. `FileGrid` keeps the chip itself when a caller passes neither prop, and still runs `categorizeMime` over whatever it is given, since search hits and `starred` never came from that endpoint; folders pass every chip, as they do in `filter_by_type` server-side. A large card's meta line is the subtitle and, from `updatedAt`, a **friendly date** — "Just now", "Yesterday", "Monday", "A week ago" (`formatFriendlyDate` in `@neutrino/utils`, which `@neutrino/ui` depends on for it); both sit on one row so the date costs no card height, and the exact timestamp is the tooltip. Only the card is friendly: the Detailed list's Modified column keeps `modifiedText`'s absolute date, since a column you sort by wants a date. That is why `/docs`, `/sheets`, `/slides` and `/notes` cards no longer carry a subtitle — theirs *was* the date. Trash rows carry `deletedAt` instead of `updatedAt`, so it is mapped onto both the Modified column and the card's date (whose subtitle is therefore the bare word "Deleted"), and Restore / Delete forever live in the row's three-dot menu (`trash/TrashContextMenu.tsx`). Folders are not addressable by URL — My Drive tracks the open folder in component state — so clicking a folder outside My Drive does nothing.

**Motion photos** — Apple Live Photos (#154) and Google Motion Photos (#156) are both "a picture that moves", and `packages/api-photos/src/motionPhoto.ts` is the whole model of it, over `quicktime.ts` (atom walking) and `xmp.ts` (packet finding and GCamera fields). They arrive shaped differently and that is most of the complexity: Apple **splits** one into two files, a still and a ~3 second clip, so the clip lands as a silent movie beside its own picture; Google **packs** one into a single `.MP.jpg` with an MP4 appended, or exports it as a bare `.mp4`, so it lands as a movie with no picture at all.

**Classification reads embedded metadata, never the extension**, and runs in the browser: photo content is E2EE, so `exiftool` server-side would be looking at ciphertext. `readMotionPhotoInfo` asks *every* uploaded file — checking only the videos is what missed the Google case — and looks for Apple's `com.apple.quicktime.content.identifier` under `moov`, then Google's `GCamera:MotionPhoto`/`MicroVideo` XMP in a JPEG APP1 segment or a movie's `uuid`/`moov/udta/XMP_` box. An ordinary video carries neither, which is what keeps ordinary videos out of the photo grid. The result — `subtype` (`live_photo_apple`/`motion_photo_google`) plus the `signal` that classified it — travels up as `metadata` on `POST /api/v1/photos`, the same reason the thumbnail does; the info panel shows the signal back, so "why is this a photo?" has an answer. A clip also gets `generateVideoThumbnail` rather than none, so a motion photo whose still never arrived is a picture instead of a black tile.

**Pairing cannot rely on the identifier**, which is why `pairMotionPhotos` matches on it *first* and falls back to the filename stem (`IMG_1234.HEIC` ↔ `IMG_1234.MOV`; `PXL_1.MP.jpg` ↔ `PXL_1.mp4`). The still's copy of the identifier is in an Apple MakerNote nothing here parses, the main library listing is served by the generic Drive endpoint and carries no photo metadata at all, and every library that predates this has no metadata either. That same Drive listing is `image/%` only, so clips are fetched separately by `photosApi.listMotionCandidates` — as candidates, not as content: one that pairs with nothing is dropped rather than turning Photos into a video library, unless it is itself a motion photo with no still. A video the *listing* returned (the archive and favourites tabs do) is kept unpaired, as before. `MotionPhotoMedia` then plays the clip over its still on hover, decrypting on the first hover only, since a screen holds dozens of them — downloading the separate file for an Apple pair, or slicing the appended MP4 out of the still's own bytes at the recorded offset for a Google one. Nothing is ever re-encoded and the original file is never rewritten.

**API clients** — `apps/web/src/lib/api.ts` re-exports everything from all `@neutrino/api-*` packages so existing code can import from `@/lib/api`. New code should import directly from the specific package (e.g. `@neutrino/api-calendar`).

**State management** — TanStack Query (`@tanstack/react-query`) for all server state. Zustand is available but used sparingly. Local UI state uses `useState`/`useReducer`.

**Feature flags — a deliberately small system, reintroduced for Team Spaces (#185).** Migration 00124 removed the previous one and every gate that read it: fifteen keys, all seeded disabled, ten still gating shipping code, so the app a deployment served depended on rows nobody had reason to revisit. Those keys are gone for good and the features they guarded are unconditional. **Do not add a flag to hide unfinished work; use a branch.**

What came back, in migration 00125, is the mechanism plus **one key, `teamSpaces`**, because Team Spaces replaces a primary navigation entry and ships in phases — it needs a switch that does not require a redeploy, which is the one property an environment variable could not give it. One key and not a family: #185 specified three per-phase sub-flags beside it, and they were dropped, because each would have been defensible alone and that is exactly how the old list reached fifteen. A feature gets one switch, and the answer to "is this on?" is one boolean.

There is now a **second key, `teamFileTransfers`** (migration 00130), and the bar it had to clear is worth knowing before proposing a third: **a difference in blast radius, not a difference in phase.** Every other Team Spaces route acts on rows a team already owns, and `teamSpaces` off makes all of them 404. The two transfer flows act on a member's own My Drive — *moving* a personal file into a team, which gives it away for good, and *sharing* one with a team, which lends it revocably through a `team_file_shares` row that `get_effective_role` honours. That is a different thing to be able to close, and closing it should not mean taking Team Spaces down. It is meaningless alone: `TeamsService::require_transfers` checks `teamSpaces` first and `canTransferToTeams` in `lib/featureFlags.ts` is the client's mirror of that, so a deployment with only the second flag on behaves exactly like one with neither. A per-phase sub-flag would still not clear this bar. `src/drive/feature_flags/` holds the table, the public `GET /api/v1/feature-flags`, the admin read/write endpoints and a `FeatureGate` the server-side gates read per request; `apps/web/src/providers/FeatureFlagsProvider.tsx` fetches the map above `AuthProvider`, and the admin panel's Feature Flags tab toggles it.

The failure mode that made the old system worth deleting is designed out rather than re-inherited. Four keys the `FeatureFlags` type declared — `docsPresence`, `docsTrackChanges`, `docsCompare`, `docsMobileEditor` — had **no row in the table at all**, so they read `undefined`, `undefined` is falsy, and four features were off not because anyone disabled them but because nothing knew they existed; two of them gated code that had therefore never run in production. So a declared key with no row is now an error at three points: `src/drive/feature_flags/catalog.rs` lists what the server declares and a unit test asserts every entry has a seeded row, the repository refuses to serve a map missing one (500, naming the key), and `apps/web/src/lib/featureFlags.ts` derives the `FeatureFlags` type from a single `FLAG_KEYS` list and throws on a response missing one. **Adding a flag means three edits — a migration, a catalog entry, a `FLAG_KEYS` entry — and the tests fail until all three agree.** A fourth thing fails too: tests in both suites assert the list is exactly what the product declares, so another flag cannot be added absent-mindedly — updating that assertion is the moment to write the argument down. Each row's description carries an owner and the condition under which the flag is removed, both rendered next to the toggle, so "can this come out yet?" is answerable where it is asked.

A gated-off route answers **404, not 403**: with the flag off the feature does not exist on that deployment, and 403 would leak a roadmap to anyone probing the routes.

**Team visibility decides who can find a team, never what a member may do in it.** Those are separate axes and they were conflated once already: `teams.visibility` shipped its first draft validated, stored, returned in the DTO and *never read* — nothing branched on it, every team behaved as private, and the Settings dropdown told owners that an "Organization" team was findable by anyone in the organization while the server ignored the column. `src/drive/teams/visibility.rs` is now the whole model: `private` is not discoverable (a non-member gets the same 404 as for a team that never existed), `organization` is discoverable and joined by adding yourself, `invite_only` is discoverable and joined by asking — a row in `team_join_requests` an Owner or Admin answers. A stored value nothing recognises reads as `private`, deliberately: the cost of being wrong the other way is a team everybody can join.

Discovery is confined to `GET /api/v1/drive/teams/discoverable`, which returns `DiscoverableTeam` and **not** `Team`. Keeping them separate types is the point — `Team` carries `userRole` and means "a team you are in", which the rest of the UI assumes; every other team route still requires membership, so a discoverable team is findable without being readable. Joining grants `viewer` and nothing more: the owner made the team joinable, which is not the same as saying anyone who wanders in may rewrite the wiki, and promoting is one click in the recoverable direction. What the Discover button says comes from the server's `joinAction`, not from `visibility` in the client, so the policy lives in one place.

**A team's disk quota is the team's, and only an administrator sets it.** `teams.storage_limit_bytes` is the limit and `null` is *unlimited* — a choice, not an absence. Every team is created with `DEFAULT_TEAM_QUOTA_BYTES` (10 GiB, `src/drive/teams/quota.rs`), and migration 00131 backfilled the teams that predate it with the same number; the two copies of that figure are held together by `the_backfilled_quota_matches_the_constant`, which runs the real migrations. Two quotas are charged for the same bytes and neither replaces the other: the uploader pays out of their personal allowance because they chose to bring the file in, and the team pays out of its own because the file now lives in a shared library that outlives whoever added it. A team with ten members and no quota is ten personal quotas pooled by accident.

**What an administrator can do to a team without being in it** is four things, one route each so each is separately auditable: set its disk quota, hand it to a new owner, archive or restore it, and delete it. They exist for the case the member-facing routes structurally cannot serve — **a team whose Owners have all gone**, where `delete_team` (Owner only) and Settings (ManageSettings) are both unreachable by everyone. So the transfer works on a team with no Owner at all, and the console renders an empty owner list as a warning rather than a blank cell; `AdminTeam.owners` is a *list* because the role is not a slot. Transferring is a **transfer**: the named account becomes Owner and existing Owners drop to Admin — demoted, not removed, so it is one click back, and the dialog says so before it happens. Adding a co-owner instead is what the team's own Members page is for. Deleting is soft, exactly as the Owner's own delete is, but nothing in the console lists deleted teams, so there is no undo there — which is why the dialog makes you type the name and points at Archive. Every one of the four writes an entry into **the team's own activity feed** with the actor recorded as `administrator`: a team finding out by hitting the consequence is the outcome that is worth a row. In the console they sit behind the row's three-dot button, in `admin/RowActionsMenu.tsx` — which was `UserActionsMenu` until the Teams table wanted the same thing, and never knew anything about a user. Both tables use it for the same reason: four to six actions per row, one of them destructive, wrap the column into something unreadable as inline buttons and put Delete a mis-click from Archive.

**The team cannot raise its own limit** — a limit a team can lift is not a limit — so `UpdateTeamRequest` carries no such field and `src/drive/teams/admin_api.rs` (`AdminUser`, `GET /api/v1/admin/teams`, `PATCH /api/v1/admin/teams/{id}/quota`) is the only route that writes the column. That file is separate from `teams::api` because the two answer to different authorities and a route drifting between them would silently change who may call it; what the admin authority buys is deliberately the *outside* of a team — name, size, member count — never its pages, files or activity. The console's **Teams** tab renders it, hidden entirely when `teamSpaces` is off since the endpoint 404s then. Lowering a limit below what a team already stores is allowed and **deletes nothing**: the files stay, the next one is refused, and the row reads `overQuota`. Occupancy is recomputed from the file rows on `GET /teams/{id}` (the read the Settings page's Storage panel displays, so it self-heals a drifted counter) and by the admin listing's own query — but *not* written back by the listing, which would turn a page view into an unbounded write.

**Moving a file into a team and sharing one with it are two different things, and each lives where its question is already asked.** A **share** writes a `team_file_shares` row: the file stays the caller's, keeps its own shares and its own quota charge, and is listed in a separate "Shared with this team" section of the team's Files page that the owner — or a team Owner/Admin — can remove it from. A **move** sets `files.team_id`: the file leaves My Drive, the team owns it, and `get_effective_role` consults membership and stops — so every individual grant on it stops applying, the mover's own ownership included. The response carries `sharesNoLongerApplied` so the client can say how many people just lost it, and there is no route back.

So sharing with a team is in the **Share dialog** and moving into one is in **Move to**, and there is no team entry in a file's context menu at all. There was: #185 shipped both as `TeamTransferDialog` behind "Add to a team space", one dialog holding a radio pair, which made the two legible against each other and invisible next to the ordinary Share and Move it duplicated — you cannot see who can open a file in a dialog that lists people while a second dialog lends it to twelve. `packages/ui`'s `ShareDialog` now searches people *and* teams from one box ("Add people or team"), lists team grants beside individual ones with a square `TeamAvatar` rather than a round one, and `MoveFolderDialog` lists teams as destinations under the My Drive folders at its top level. That top level has **no breadcrumb**: "My Drive" as the only crumb above My Drive's own folders labelled the thing you were looking at, and the trail now appears on the way in, rooted at "My Drive" or at the team. What the old dialog's radio pair said in words, the new places say in shape — the irreversible one is a red button under a warning, armed only once the browser is inside a team.

Two supporting pieces are worth knowing. Teams are filtered **client-side** in the Share picker, from the caller's own `teamsApi.list()`: there is no team search endpoint, because a team you are not in is not findable by name unless its visibility says so. And `GET /api/v1/drive/files/{fileId}/team-shares` (`teams::api`, the one route there that hangs off a file) is what fills the access list — the file's side of the same rows `list_shared_files` reads from the team's side, owner-only, and 404 for a file that is not the caller's own, which is the same answer the write routes give. Both roles a team can hold are `viewer` and `editor`; the picker narrows to those the moment a team is chosen, since `commenter` has no meaning for a team and `owner` is refused by the server.

Both are two calls from the client, and the order is forced by encryption. **A file's DEK is sealed per person, so granting a team access is not the same as making the file readable**: the server can write the row and nothing more, since the plaintext key exists only in a browser that already holds it. `lib/teamTransfer.ts` does the second half — reseal the DEK to each team member — and it has to run *after* the transfer, because `POST /encryption/files/{id}/share` refuses a recipient with no access yet (`RECIPIENT_NO_ACCESS`). Skip it and the team sees a file in the listing that none of them can open. Nothing in it is fatal: a plaintext file has no DEK, and a member whose public key has changed since this browser pinned it is *named in the toast rather than sealed to blind* — the one-to-one Share dialog stops for a fingerprint comparison there, and a queue of those in front of a bulk action is not the same trade.

**User preferences** — persisted in `localStorage` and read back on mount with a `storage` event listener for cross-tab sync. The pattern is used for theme (`neutrino.theme`), calendar week start (`neutrino:calendar:weekStart`), and similar settings. Preferences are not stored in the backend unless they are part of `UpdateProfileRequest` (handled by `authApi.updateProfileDetails`).

**AI features** — every one of them (the Diagrams generator, Sheets Explore and the conditional-formatting rule builder, Slides authoring help, Photos vision tools, the Docs grammar fix) runs on the provider and API key the user sets in **Settings → AI Assistant**. The settings live in `localStorage` under `neutrino.ai.settings`, but the reader is in `@neutrino/api-core` (`readAiSettings`/`aiCredentials`), not in the app: each `xxxAI` client method spreads `...aiCredentials()` into its request body, so a new AI endpoint gets the credentials by construction and no call site has to thread them through. `useAiSettings` is the settings page's view of the same storage, not a second copy of it.

The request then goes to the **Rust backend**, which proxies it to Anthropic, OpenAI or Google (`src/shared/ai/`) — one `AiClient` for all three, so an app module never sees a provider's wire format and every feature works with whichever provider is configured. Features with no server-side logic of their own call `aiApi.complete` (`POST /api/v1/ai/complete`); the rest have their own endpoint that does something with the answer before returning it. Nothing calls a provider from the browser, and the server holds no key: `ANTHROPIC_API_KEY` is gone.

The route handlers under `apps/web/src/app/api/` that used to serve this are gone with it, and nothing should replace them: production is `output: 'export'`, so a Next route handler exists in dev and is a 405 from the Rust server in the deployed app — which is what issue #139 was.

**Calendar app** — `apps/web/src/app/(apps)/calendar/page.tsx` is the main client component. It owns all state: current view (`month` | `week` | `agenda`), cursor date, event/reminder CRUD mutations, ICS drag-and-drop, and browser notifications. View components (`MonthView`, `WeekView`, `AgendaView`) are pure presentational and receive `cursor`, `events`, `onDayClick`, `onEventClick`, and `startDay` props. Helper functions (`eventsForDay`, `weekStartDate`, `expandRecurringEvents`, etc.) are in `calendarHelpers.ts`. Constants (day/month names, reminder presets) are in `calendarConstants.ts`.

**Settings** — the `/settings` page (`apps/web/src/app/(apps)/settings/page.tsx`) is tab-based. The Calendar tab stores the `weekStart` preference in localStorage via `WEEK_START_KEY`. The calendar page listens to the `storage` event to pick up changes without a page reload.

**Settings and Profile split what they own** (issue #60). `/profile` is **who the user is** — avatar, display name, bio, website, locale, social links — and `/settings` is **how the app behaves**. They used to overlap: the theme grid, the four email-notification checkboxes and the display-name field each existed on both, with separate state and separate save buttons, so whichever screen you were not looking at showed a stale copy. A new field goes to exactly one of them by that rule; `/profile` carries a line pointing at Settings for the rest. Within Settings, a tab is split before it gets crowded rather than after — **Security** (password, the whole encryption-key panel) exists because Account had grown to hold identity, password, encryption and account deletion at once. Account is now the address, a link to `/profile`, and the danger zone. Every "Set up encryption" link in the editors (`EncryptionWarningMessage`) deep-links to `?tab=security`.

The display name is the one field on `/profile` that is **not** in `UserProfileDetails`: it lives on the user row, so `PUT /api/v1/auth/profile` takes it as an optional `name` and writes it through `update_user_name`, and it is not echoed back in the response. The page therefore calls `useAuth().refresh()` after a save — without it the topbar and every avatar keep the old name until a reload. Sending no `name` leaves the account's name alone, which is what every other caller of that endpoint (the theme picker, the notifications tab) relies on.

**UI library** — `@neutrino/ui` exports primitives (Button, Text, Heading, Badge, Avatar), inputs (TextInput, Select, Checkbox, Radio, Toggle, SearchInput), feedback (Alert, Toast/ToastProvider, Spinner, Skeleton, EmptyState, ProgressBar), containers (Card, Modal, Panel, Popover, Drawer, Tabs, Accordion), and navigation (Menu, Dropdown, Breadcrumbs, Pagination). CSS is CSS Modules with `var(--color-*)` design tokens.

**Inserting images** — every editor adds images through one control, not its own dialog. `ImagePickerDialog` (`@neutrino/ui`, `components/panels/`) is the presentation half: three sources — **Neutrino Drive**, **Local File**, **URL** — sharing one preview pane, and it will not enable Insert until that preview has actually decoded, which is also how a 404 or a non-image URL is rejected without the caller validating anything. Like `FillPicker` and `SaveAsDialog` it takes its data through callbacks (`onFetchDriveImages`, optional `onUploadLocalFile`) because `@neutrino/ui` has no API dependencies. `@/components/InsertImageDialog` is the connected half every app should import: it lists the caller's Drive files and keeps the images by MIME type (`storageApi.listFiles` accepts a `type` filter in its query type but drops it before the request), browses off `coverThumbnailUrl` where one exists (`storageApi.getThumbnailUrl` turns it into an `<img src>`), and uploads through `storageApi.uploadFile`. `localFileMode` decides what a local file becomes — `upload` (default; stored in Drive, inserted by URL, as slides does) or `embed` (base64 data URL, keeping the document self-contained, as docs does). `defaultSource` opens the dialog on a given tab, which is how the docs toolbar's separate "Upload local image" button still lands somewhere specific.

**Images are references, not bytes** — `apps/web/src/lib/driveImages.ts` owns this. A document stores `neutrino-drive:<fileId>` where an `<img>` src would go; the file lives in Drive and the bytes are resolved at render time. Every source ends up a Drive file: a Drive image already is one, and local files and linked URLs are uploaded into an **Attachments** folder (`ATTACHMENTS_FOLDER_NAME`, created for new accounts by `register` in `src/auth/api.rs` and get-or-created client-side for accounts that predate it — keep the two names in step). A URL import is fetched *by the browser*, so a host that refuses cross-origin reads can't be copied; that failure is reported as "add it from the Local File tab" rather than as a fetch error. An attachment is a Drive file like any other and is **encrypted like any other**: `uploadAttachment` follows the same rule as `UploadZone` — generate a DEK, seal it to the user's public key, upload ciphertext through `uploadEncryptedFile`, and generate the thumbnail on the device (the server can't preview what it can't decrypt) — falling back to a plaintext upload only when the session holds no keypair. Nothing on the read side cares: `fetchDriveImageBlob` decrypts when `encryptedMetadata` is set and passes the bytes through when it isn't, so attachments stored plaintext before this still render.

Resolution is asynchronous but rendering isn't, so the two are bridged differently per editor. Docs uses `DriveImageExtension` — a ProseMirror plugin that paints the resolved src on with a **node decoration**. Not a node view (that would replace `AdvancedImage`'s `renderHTML` and lose width/alignment/border/shadow/filter, or wrap the `<img>` in something the CSS doesn't expect) and never an attribute write: an attribute would be serialised by the next autosave, putting a dead blob URL or the bytes back in the file — the exact thing references avoid. `DriveImageExtension.test.ts` pins that down. Slides uses the `DriveImage` component / `useResolvedImageSrc` hook in `SlideRenderer` and `SlideCanvas`. A slide **background** is part of the presentation too, so it is stored the same way: `FillPicker` takes an `onStoreImage` hook that turns a picked image (Drive item, local file, or URL) into the value to store, and the slides wrapper returns a reference from it — without the hook the picker keeps its old behaviour, which is what `/drawing` still uses. Reading them goes through `useSlideBackgroundStyle`, because a reference cannot sit in a CSS `url()`; every surface that paints a slide (`SlideCanvas`, `SlideThumbnail`, `PresenterView` ×2) uses it. `pptxExport` inlines a referenced background as a data URL for the same reason exports do.

Still byte-carrying, deliberately: `pptxImport` builds image elements as data URLs from the archive, and `Theme.backgroundImage` holds preset URLs that no user upload path writes to. Export and print inline the bytes with `inlineDriveImagesInHtml`, because a PDF, a .docx or a print window has no way to resolve a reference. Non-references — `http(s):`, `data:` — pass through everywhere untouched, which is what keeps documents written before this rendering. Resolved bytes and the Attachments folder id are cached per session and cleared on sign-out (both are per-user).

The part worth knowing before touching any of it: **a Drive file's download URL is not always the image**. E2EE files (`encryptedMetadata` non-null) store ciphertext, and an `<img>` pointed at one gets a 200 and then fails to decode *silently* — nothing rendered, nothing in the console — while the grid beside it still looks right, because the cover thumbnail is a separate unencrypted preview, served from its own URL (`coverThumbnailUrl` → `GET /api/v1/drive/files/{id}/thumbnail`) since issue #175. So `onResolveDriveImage` downloads and decrypts in the browser (the only place the key exists: `loadKeyPair` → `encryptionApi.getFileKey` → `decryptFileKey` → `decryptFile`, the same sequence `PhotoEditor` uses) and hands back a data URL, while unencrypted files short-circuit to their URL with no download at all. Whatever was previewed is what gets inserted, so an encrypted image is embedded as plaintext bytes — correct, but it means a large encrypted photo lands in the document as a multi-megabyte data URL. The way out is render-time decryption in the editors keyed off the `driveFileId` already stored on the inserted node; until that exists, don't "optimise" the picker by inserting the Drive URL instead — that is the bug this replaced.

**Back navigation pattern** — pages that need a back button (profile, users, etc.) use a raw `<button>` with a `backBtn` CSS Module class alongside `<ArrowLeft size={16} />` from lucide-react and `router.back()` from `useRouter`. The `backBtn` style is transparent, `font-size: 13px`, `color: var(--color-text-secondary)`, and turns `var(--color-primary)` on hover. It sits above the `<h1>` heading inside the `.header` div.

**Tests** — Vitest + Testing Library + jsdom. Config is at the repo root (`vitest.config.ts`). Tests live alongside or under `src/__tests__/` inside each app/package. The `@` alias resolves to `apps/web/src`. API modules are always mocked with `vi.mock` — no real HTTP calls in tests.

**Google Takeout import** — `/import` (`apps/web/src/app/(apps)/import/page.tsx`), reached from the Topbar user menu below Settings (`onImport` on `Topbar`, wired in `(apps)/layout.tsx`). Everything runs client-side in `apps/web/src/lib/takeout/`: `archive.ts` opens the zip and groups entries by product directory (the `Takeout/` wrapper is detected by shape, not by name, so localised exports work), and each product then has a converter plus a runner.

`archive.ts` reads with **zip.js, not JSZip** (which the app still uses elsewhere, e.g. the pptx importer). This is the one thing to preserve if that module is ever rewritten: a Takeout export runs to gigabytes, and JSZip's `loadAsync` reads the whole file into an `ArrayBuffer` before it can list it, which capped the feature at what a tab could allocate — to import documents that are a rounding error beside the photos in the same archive. zip.js's `BlobReader` seeks with `Blob.slice`, so opening reads only the central directory at the tail (~64 KB whatever the archive size) and each `text()`/`blob()` inflates one entry, in a worker. Peak memory is the largest file, not the archive; `archive.test.ts` pins both properties down by counting bytes sliced. The reader stays open for the archive's life, so the page closes it on reset and on unmount. The import cannot live on the server: note, document, spreadsheet, presentation and photo content is E2EE, so only the browser holds the DEK — each runner mints one per item and registers it with `encryptionApi.setFileKey`, exactly as an editor's first save does (photos instead upload through `uploadEncryptedFile`, which carries the key with the file). Five products are supported and the page runs them in sequence, sharing one progress bar and one result screen (`types.ts` holds the `ImportSummary`/`ImportItem` shape they all report in, `folders.ts` the cached folder-path resolver they all use).

**A split export is one archive, not several.** Google splits an export at a size the user picks when requesting it — 2 GB by default, so a large Photos library arrives as dozens of `takeout-…-001.zip` parts — and it splits between files, never through one, with the same `Takeout/` wrapper on every part. `openTakeout` therefore takes either one zip or all of them: it opens each (in sequence, since each reader brings its own worker pool), merges the product directories by name, and presents the union behind the same `TakeoutArchive`, so nothing downstream knows the difference and an entry still reads from whichever zip it came out of. Importing the parts one at a time instead is not the same import — an album and the photos it names, or a sidecar and the file it describes, routinely land in different parts. Entries are deduplicated **by path**, which is what makes picking the same part twice harmless; deliberately not by name and size, because Google files a photo under both its album and its year and folding *those* together is `photos.ts`' job, done after this. `archive.close()` closes every part, and `partCount` is on the archive for the page to report.

- **Keep → Notes** — `inlineHtml.ts` turns Keep's HTML into the editor's inline markdown, `keep.ts` converts a note into `Block[]`, `importKeep.ts` drives the run.
- **Drive → Docs** — a Google Doc is a Drive file, so it lands in `Takeout/Drive/` as `.docx` (the export default), `.html` or `.txt`; `driveDocs.ts` picks those out of everything else in the export and `importDocs.ts` drives the run, mirroring the export's folder tree via `folders.ts`. Formats the browser can't convert (`.pdf`, `.odt`, `.rtf`) are counted and reported rather than silently missing. **A `.docx` export is stored byte for byte** (`storedDocxFor`): a document *is* a `.docx` now (issue #127), the editor opens it with `readDocx` like any other Word file in Drive, and there is nothing to convert. It used to go through mammoth into HTML and on into Tiptap JSON, which was right when a document was stored as that JSON and became a lossy round trip to nowhere once it wasn't — mammoth is built to discard presentation, so every colour, alignment, indent, header and footnote in the export was dropped on the way in. `.html`/`.txt` have no such shortcut, so they still convert through `docHtml.ts` (by hand rather than through `DocEditor`'s extension list, which would pull the editor into the import bundle — so it emits only nodes every feature-flag configuration understands) and are written out with the editor's own `writeDocx`. Either way the bytes go up through the binary-safe transport; writing the bespoke `doc.json` body instead is what left every imported document reporting "Failed to open this file for editing", which is issue #169. The search index is built by reading the stored bytes back with `readDocx`, so it holds what the editor will show — and a document that won't parse loses its full-text search rather than its import.
- **Drive → Sheets** — a Google Sheet is a Drive file too, arriving as `.xlsx` (the export default), `.csv` or `.tsv`; `driveSheets.ts` is the docs finder's counterpart, `sheetXlsx.ts` converts the bytes into the editor's `SheetFile` JSON with SheetJS (dynamically imported, and by hand rather than through `SheetEditor`, for the same bundle reason), and `importSheets.ts` drives the run. `.ods` and `.xls` are the reported-but-unconvertible cases. **A `.xlsx` export is stored byte for byte** (`storedXlsxFor`), for exactly the reason a `.docx` is: a spreadsheet *is* an `.xlsx`, and `ooxml/xlsx/read.ts` opens the exported one directly, so there is nothing to convert and everything to lose by converting. Only a `.csv`/`.tsv` is written out, through the editor's own `writeXlsx`, and there the tab name is repaired on the way in since Excel rejects several a file can legally be called. Writing the bespoke `sheet.json` instead was the other half of issue #169, and the quieter half: SheetJS reads JSON text as a one-row CSV, so the spreadsheet opened as its own source code across row 1 rather than reporting anything. As with docs the search index is built by reading the stored bytes back with `readXlsx`. The conversion's one rule worth knowing: `raw` holds the *unformatted* value and the export's number format rides along as `cellStyle.customFormat`, which the editor's `applyCustomFormat` reads in the same Excel notation — so a percentage stays a number you can sum, and a date stays the serial it is in the file rather than a date string the browser's timezone could shift by a day. `cellStyles: true` is set on the read only because that is the pass in which SheetJS parses `<cols>` and row heights; cell styling itself is not imported.
- **Drive → Slides** — a Google Slides deck is a Drive file as well, arriving as `.pptx` (the export default); `driveSlides.ts` is the third finder over the same directory and `importSlides.ts` drives the run. There is no conversion module at all, and that is the whole design: a presentation *is* a `.pptx` (issue #127) and `SlideEditor` opens the exported one with `importFromPptx` like any other PowerPoint file in Drive, so `storedPptxFor` stores the export byte for byte. Rebuilding it through the editor's model on the way in would cost everything pptxgenjs cannot carry — themes, transitions, gradient backgrounds, speaker-note formatting — for nothing. `.odp` and `.ppt` are the reported-but-unreadable cases; `.pdf` and `.txt` deliberately are **not**, because a PDF in Drive says nothing about which app wrote it and the docs finder already reports both. The search index is built by reading the stored bytes back with `importFromPptx` (dynamically imported — it pulls JSZip and the whole parser) and flattening them with `extractSlideText`, and as with docs a deck that won't parse loses its full-text search rather than its import.

- **Google Photos → Photos** — `photos.ts` finds the media and `importPhotos.ts` uploads it, encrypted, exactly as the Photos app's own upload does (`uploadEncryptedFile` → `photosApi.registerPhoto`). Three things there are load-bearing. **The thumbnail is generated on the device** (`generateThumbnail`) and sent with the upload, because the server cannot make a preview of a file it cannot decrypt — skip it and the library is a grid of blank tiles. **A photo in an album is written twice by Google**, into the album folder and into its year folder, so copies are folded together by name and size and the album folders become the albums the one uploaded copy joins; without that, every album photo lands in the library twice. **The capture date has one accepted format**: `POST /api/v1/photos` parses `%Y-%m-%dT%H:%M:%S` and nothing else, so `captureDateOf` trims the `Z` and the milliseconds `toISOString` adds — send those and the date is dropped in silence, leaving the photo undated in a library sorted by date. Location and camera details are deliberately not read from Google's sidecar: the original bytes are uploaded untouched, so the server reads them from the file's own EXIF. `Archive` and `Trash` are recognised by name (English only) and become the archived/trashed flags the run's options act on.

  Media is found in three places, in that order of preference: a product directory named for Photos; a `Google Photos` folder **nested inside another product**, which is where pictures land when they reached Drive rather than Photos (`Takeout/Drive/Google Photos/…`) and is re-rooted by `nestedPhotosDirs` so the rest of the module sees an ordinary directory; and last, for a localised export, whichever product scores highest on media files that have a `.json` sidecar. The order matters and so does the asymmetry: a directory *named* for Photos is taken at its word and its media needs no sidecar, because the Drive-hosted case has none at all — no sidecars, no albums, no archive or trash, and no capture date except what the server reads out of the file's own EXIF. The sidecar score stays the rule for the unnamed case only, since without it Keep's attachments and any Drive full of pictures would qualify.

All three Drive products read the same directory, so locating it, pairing a file with its `-info.json` sidecar and reading one live in `drive.ts`. The directory is found by name or, for a localised export, by the extension only Drive emits — `.docx` for the docs pass, `.xlsx` for the sheets pass and `.pptx` for the slides pass, never `.html`/`.txt`/`.csv`, which other products write (Keep puts an `.html` beside every note, Contacts exports a `.csv`).

**Imported files keep their own dates.** Every runner ends a file by calling `storageApi.setImportMetadata` (`PATCH /api/v1/drive/files/{id}/import-metadata`), which is what `lib/takeout/importMetadata.ts` exists for. It has to be a second call, after the content: writing a body is what stamps `updated_at` with the current time, so anything set at creation is overwritten a moment later. Before this, every date on every imported file was the moment of the run — issue #110 — which made Drive's created/modified sorts meaningless and the photos timeline a single day. Where the dates come from differs per product and the shapes do too: Drive puts ISO strings in the `-info.json` sidecar under key names that have moved between Takeout versions (`drive.ts` reads several spellings of each); Keep writes `createdTimestampUsec`/`userEditedTimestampUsec` in **microseconds**; Photos writes `photoTakenTime.timestamp` in **seconds, as a string**. `isoFromEpoch` takes the unit as a parameter rather than sniffing it from magnitude, because Keep's microseconds read as seconds is the year 46,138 rather than an obvious failure. The universal fallback is the zip entry's own `lastModified`, which `archive.ts` now carries — it fills *both* dates, since filling only the modified one leaves the created date at the import's clock, i.e. half the bug. Dates that mean "unset" (a 1980 DOS timestamp, a zero epoch) are dropped rather than written, and a failed call only warns: the content is already uploaded by then, so failing the item would report a good file as a bad one and invite a second import of the whole archive. The rewrite is recorded on the row — `imported_at` and `import_source` (the entry's path inside the archive), added by migration 111 — which is both the provenance the issue asked for and the only remaining way to tell an imported file from a native one now that `created_at` is a date from 2014.

For photos the capture date matters more than the file dates, because the library is *sorted* by it: `importPhotos.ts` falls back to the zip entry when there is no sidecar, which is the case for every picture that reached Drive rather than Photos. The Drive row behind a photo takes the capture date for both of its dates — for a photo they are one event, and the export carries nothing that means "modified" beyond when Google built the archive.

To add a product, add a converter module plus a runner returning an `ImportSummary`, a section in the page, and a step in the page's `buildSteps`.

**The run outlives the page.** `/import` owns picking the archive and choosing what comes across; it does *not* own the run. That lives in `ImportRunProvider` (`components/ImportRun/`), mounted in `(apps)/layout.tsx` above the route, so switching to another app leaves both the import and its progress bar alive — the page reads `useImportRun()` and a run in progress wins over its own stage, which is how coming back mid-import lands on the progress bar instead of on the file picker. The provider knows nothing about Keep or Drive or Photos: the page hands it `ImportStep[]` (a product label, an item count, and a `run`), and it sequences them, adds their progress into one bar, and stops the rest when one reports `cancelled`. Three things moved there because they have to outlive the page: the abort controller behind Stop, the query invalidation, and **the archive handle** — ownership transfers with the plan, so the zip reader is the provider's to close and the page's unmount cleanup must not (`archiveRef.current = null` on start is what hands it over). A `runningRef` guard rejects a second `start` while one is going, which is what stops a remounted page uploading the same files twice.

**A failed file can be run again** (issue #155), and that is what decides when the reader is closed. The result screen offers Retry per failed row and Retry all, and `retry(targets)` sits on the provider beside `start` for the same reason the run does — the screen is reachable after a route change, so neither the plan nor the archive a retry re-uploads from can live on the page. So a run that ends with **nothing** failed closes the archive the moment it ends, as it always did, and one with something still to retry keeps it open until the retry leaves nothing over, the run is dismissed, or another starts; `state.retryable` is what says which, and the page shows the buttons only when it is set. The provider stays product-ignorant: it groups the targets by product label and re-runs the steps it already holds, each given an `only` set of file paths that the *step* filters its own list with — every runner reports an item's `file` as the entry's path in the archive, so that is the key on both sides and no runner needed changing. What comes back is merged into the run rather than replacing it (`mergeResults.ts`): rows are replaced by `file` and the counts move by the difference, since a retry of 3 items out of 5,000 that reported itself as the whole import would read as "3 imported". `cancelled` and `unencrypted` are sticky across a merge — a stopped run left items it never attempted, and retrying the ones it did does not change that. A retry re-runs an item from the start, so one that failed half-way can leave the first attempt's partial file behind; each product's "Skip … that already exists" option is what covers that today. `useImportRun` throws outside the provider rather than returning an idle stand-in, because a stand-in makes `start` a silent no-op — an Import button that does nothing. While a run is going the provider shows a floating progress pill on every route except `/import` (which renders the run in full) and registers a `beforeunload` warning, since a reload or a closed tab is the one thing that still kills a run: none of this is on the server.

Every stage logs to the console through `log.ts` (`[takeout:archive]`, `[takeout:keep]`, `[takeout:docs]`, `[takeout:sheets]`, `[takeout:photos]`, `[takeout:folders]`, `[takeout:page]`) — an import is a long unattended run over files we didn't write, so the console is the only record of which file failed and where. `describeError` turns an API rejection into `HTTP <status> <code>: <message>`, and every runner uses it for the reason shown against a failed item, so a 413 or an expired session is legible on the result screen rather than arriving as a bare message. Logging is unconditional: the failure has already happened by the time anyone would think to turn a debug flag on.

**Font import is a zip read in the browser, then ordinary uploads.** The admin console's Fonts tab (`app/(apps)/admin/FontsTab.tsx`, over `fontArchive.ts`) takes a drop of anything — one font, several, a family zip, several zips — lists what it found with a tick and an editable name per row, and uploads each ticked row through `POST /api/v1/admin/fonts`, the same endpoint a hand-picked file always used. Nothing about the server changed, and that is the decision: the endpoint already validates a font (extension against declared MIME, 50 MB, streamed to a guarded temp file), so a server-side expander would be a *second* upload path — zip bombs, path traversal, a staging directory — arriving at the same place, and the archive has to be read before anything is uploaded anyway, since the whole point is to show what is inside and let the admin choose. Server-side that would be an upload, an inspect and a commit with state parked in between.

Three things in it are load-bearing. **Nothing is inflated until it is uploaded**: listing reads only the zip's central directory, exactly as `lib/takeout/archive.ts` does, so an archive where twenty-four of twenty-six weights are left unticked never decompresses the twenty-four — which is why the zip readers outlive the drop and are closed when the list empties rather than when it is built. **A single `.ttf` goes through the same list as a zip of eighteen**, because the list is where the name is decided and fast-pathing the one-file case would mean two install paths that could disagree about naming. And **the run is sequential and reports per row**: what installs leaves the list, what fails stays on it with its reason, so the retry is the same Install button rather than a second pass over the archive. `displayNameForFont` is the generated name — separators and case changes become word boundaries, a variable font's `[wdth,wght]` axis list comes off — and every row keeps it as an editable field, since the suggestion is right often enough to make the list a matter of reading and wrong often enough to need overriding.

**Notes live updates** — the note editor (`apps/web/src/app/(apps)/notes/editor/page.tsx`) stays in sync with edits made by another user or another device. `useFileSync` (`apps/web/src/hooks/useFileSync.ts`) opens a relay socket at `/api/v1/files/{id}/ws` — the shared, file-type-agnostic endpoint (backend: `src/shared/file_events/`, backed by the same generic `PresenceRoom` sheets and slides use for their own separate sockets; notes is its only caller so far). The relay carries a *signal* only — `{ clientId }`, never file content — because notes are E2EE; on receiving one the editor invalidates the `['note', id]` / `['note-content', id]` queries and decrypts the fresh content locally. A local autosave broadcasts the signal after the PATCH succeeds. Guards in the editor: `dirtyRef`/`savingRef` stop an incoming revision from overwriting unsaved keystrokes (local autosave stays last-write-wins), `editSeqRef` keeps that protection alive for keystrokes typed while a save was in flight, and `appliedUpdatedAtRef` records the revision on screen so our own saves never trigger a re-read. While the socket is down the metadata query polls every 15 s as a fallback (`refetchInterval: connected ? false : OFFLINE_POLL_MS`).

**Collab sync only runs with company** — docs, sheets, slides and diagrams each open a collab socket on load (`usePresence`, `useSheetPresence`, `useSlidePresence`, `useDiagramCollab`), but **document content is only put on the wire while another client is in the room**. Presence/awareness is exempt and keeps its 10 s heartbeat — it is the channel that tells a client a peer has arrived, so gating it would make the gate unopenable. Everything else is buffered: slides keep the newest presentation, sheets keep the latest value per cell (`Map<sheetIndex, Map<cellId, …>>`), docs and diagrams keep their Y.Doc updates. The buffer is flushed the instant `remoteUsers` goes from empty to non-empty, so a peer that joins mid-session sees the work done before it arrived. None of this risks the file: content is persisted by each editor's own encrypted autosave, not by the socket.

Two of the sockets *do* hold state the flush has to reach anyway. The docs and diagrams rooms keep a server-side Y.Doc (`src/docs/collab/`, `src/diagrams/collab/`) which is persisted when the last session leaves and seeded into the next one — `DocEditor` prefers it over the stored file when it is non-empty, and `DiagramEditor` applies whatever SyncStep2 carries. So those two also flush on teardown, on `pagehide`/`beforeunload`, and whenever the tab goes hidden; a full-state update is idempotent server-side, so flushing repeatedly is free. `usePresence` additionally always sends the *first* update of a session — that is the editor seeding the Y.Doc from the stored file, and the server needs it or a client connecting a moment later finds the room empty and seeds a second, divergent copy of the same content. A hard crash (never hidden, never unloaded) can still strand solo edits in the browser; the file is safe, but the room's copy will lag until the next session flushes it. `__tests__/collab/soloSync.test.ts` pins the whole rule down.

**Search index changes** — nothing is searched server-side: the topbar drop-down, the Drive search view (`/drive?q=…`) and `/search` all read one IndexedDB index (`packages/search`) that every app writes to — editors on save (`lib/searchIndexUpdate.ts`), the periodic sync (`lib/searchIndexer.ts`), and the cross-device snapshot exchange (`lib/searchIndexSnapshot.ts`). Because those readers hold their hits in component state, the write paths announce themselves through `packages/search/src/events.ts`: `IndexEngine`, `clearSearchIndex` and `importSnapshot` call `emitSearchIndexUpdate`, and readers subscribe with `useSearchIndexUpdates` (`apps/web/src/hooks/`) to re-run their query. Emit from the write path itself, after the write lands, so a new way of touching the index can't forget to notify and no listener re-reads too early. Updates are coalesced over 250 ms (a rebuild writes one document at a time) and carried to other tabs over a `BroadcastChannel` — the index is shared storage, so a save in the Docs tab changes what the Drive tab would return with no code running there. "Reload the index" means re-query: the entries are already in IndexedDB by the time the event fires. Cross-*device* notification is a different mechanism — the encrypted snapshot, pulled on app start and tab focus.

**A spreadsheet is an `.xlsx`, and only that** — `apps/web/src/lib/ooxml/xlsx/`. `write.ts` and `read.ts` are two halves of one mapping (`__tests__/ooxml/xlsxRoundTrip.test.ts` asserts they agree, and that SheetJS reads the output the same way): values and formulas as `<v>`/`<f>`, number formats as `numFmt`, fonts/fills/borders/alignment as `styles.xml` entries cells point at, merges as `<mergeCells>`, column widths as `<cols>`, row heights as `ht`, a tab colour as `<tabColor>`, conditional formats as `<cfRule>`, a table region as a real `xl/tables/` part. This replaced the `neutrino/model.json` part sheets used to carry (issue #169's root cause): what the editor could write was a value per cell, so every save shipped a second complete copy of the model and the workbook beside it was decorative — and a file round-tripped through Excel came back with no model, to be read by a twenty-line SheetJS fallback that returned `cell.w`, the *formatted* string. The parts are assembled by hand with JSZip because SheetJS's community build cannot write styles, conditional formats or tables at all.

Three things have no SpreadsheetML home and go to `customXml/item1.xml`, indexed by position, on the same terms as `docx/mapping.ts` — drop the part and every cell, style and rule still reads. **Charts** (twenty types, annotations, trendlines; no OOXML chart part is written, and this is the one thing still carried whole), **the conditional-format kinds OOXML has no operator for** (progress bars, status indicators, heat-map presets, theme tokens, variable references — an approximation *is* written for each so Excel shows the cell as flagged), and **small attributes with no home**: a table's Neutrino `styleId`, `clip` as distinct from `overflow`, the CF variable definitions. `writeXlsx` also takes the previously stored package and copies forward the parts it does not model — a pivot table, an image, a chart part from Excel — so an autosave does not silently delete them; `usePersistence` holds those bytes in `storedPackageRef` for the session. The reader is the *only* reader: office-mode load, the local `.xlsx` import in `SheetEditor`, the `.xlsx` export in `useExport`, the preview modal via `documentContent.ts`, and the Takeout import all go through it, and `readNeutrinoModel` survives on the read path only, to migrate spreadsheets saved before this.

**A diagram is stored in one of two formats, and the file's mime type is which one.** The native one is the document's own JSON under `application/x-neutrino-diagram`; the other is a plain `image/svg+xml`. There is no second private mime type and there must not be one — the whole point of saving as SVG is that the file *is* an SVG, so a browser, a design tool or a README renders it with nothing installed. What makes it reopenable here is a `<metadata id="neutrino-diagram">` element carrying the document as base64 JSON, which every SVG reader ignores and no label, colour or `<` in the document can break out of. `packages/api-diagrams` owns the container (`embedDiagramSource`/`extractDiagramSource`, `diagramFormatForMime`) so `extractDiagramText` can index an SVG-stored diagram off its source; `diagrams/editor/io/svgFormat.ts` owns the typed half.

`DiagramEditor` reads the format on load and **writes back the one it opened** — a `.svg` in Drive must not quietly start holding JSON — and the menu's two `Save a copy as…` entries are how you get the other one. A copy, never a conversion in place: changing a file's mime type breaks every `<img>`, README and shared link pointing at it, and there is no route back. The SVG body is rendered from the model by `diagramDocumentToSvg`, not by serialising the live canvas, so a save carries no viewport transform, selection handles or other people's cursors and does not need a mounted DOM node; image fills are resolved to data URLs, since an `<image href>` at a Drive object is a hole in every renderer outside this app and outside this app is the reason to save as SVG. An SVG document is one canvas, so the picture shows the page that was open (recorded as `svgPageIndex`) while the embedded source carries them all.

Two consequences worth knowing. **Every `image/svg+xml` in Drive routes to `/diagrams/editor`**, ahead of the `image/` rule that sends pictures to Photos — the diagrams canvas is the only vector editor here, and the photo editor is a raster one that could only display an SVG. And because most SVGs in a Drive are not diagrams, **the editor refuses an SVG with no diagram inside it** rather than opening it as a blank canvas: the seal-plaintext pass and the autosave would both write an empty diagram over somebody's artwork, and an SVG has no version history saying what it used to be. That screen shows the picture as a `data:` URL in an `<img>` — never as markup in the page, since an SVG can carry `<script>` and this one may have been shared by someone else — and offers to build a *new* diagram around it. `__tests__/diagrams/foreignSvg.test.tsx` is what stands between that and data loss; don't relax the guard without it.

**A drawing is a layer tree on a fixed-size canvas, and it exports to OpenRaster.** `apps/web/src/app/(apps)/drawing/editor/document/` is the model: a `DrawingDocument` with a `canvas` (width, height, DPI, background), a root `StackNode`, guides, grid, colour profile and metadata; underneath it `StackNode` (a group), `RasterLayerNode` (pixels), `VectorLayerNode` (shapes) and `TextLayerNode`, each carrying the fields `agent_docs/drawing_app_redesign.md` §1 asks of every object — UUID, name, parent, visibility, opacity, blend mode, lock, transform, bounds, timestamps — plus an optional mask. This replaced a flat `Shape[]` with a `layerId` pointing into a flat `Layer[]`, which could express exactly one level of grouping of exactly one kind of content: no nested groups, no pixels, no masks, no blend modes, and no opacity below the object level. There is **no migration and no reader for the old shape**; `parseDocument` returns null for anything that is not version 2, and the editor opens a new document for an empty body and *refuses to open at all* for a non-empty one it cannot parse — the same rule the diagrams canvas applies to a foreign SVG, and for the same reason.

Three conventions run through it and each is silent when broken. **`children[0]` is the topmost layer**, which is OpenRaster's own rule, so the writer never reverses anything and `tree.paintOrder` is the single place the order is flipped for rendering. **`parentId` follows `children`** — every insert and move sets it and `normalizeTree` rebuilds the index on load, so a hand-edited or foreign document cannot arrive with the two disagreeing. And **`bounds` is cached derived state**, recomputed by `refreshBounds` on load and on save rather than maintained at each edit site, because the OpenRaster writer sizes each layer's PNG from it.

**The canvas has a size** because OpenRaster's `<image>` requires `w` and `h`, and an unbounded plane has no honest answer for them, no anchor for a guide or grid origin, and no frame for a layer offset. So a drawing is a page you pan and zoom around, as it is in Krita and Photoshop, and `render/renderDocument.ts` is the *one* renderer behind the screen, the PNG export, the merged image and each layer in the `.ora` — so what a drawing looks like on screen and in a saved file cannot drift apart. It buffers only when it must (a blend mode, a mask, an isolated group, a group below full opacity); everything else draws straight into the target, because `globalAlpha` applies per operation and compositing a group's children one at a time at 50% darkens every overlap.

**OpenRaster (`.ora`) is an interchange format, not a storage format.** `io/ora/` writes a real package — `mimetype` first and uncompressed, `stack.xml`, one PNG per leaf layer under `data/`, `mergedimage.png`, `Thumbnails/thumbnail.png` — and reads one back through **File → Import OpenRaster…**. `image/openraster` is still deliberately **not** a native type in `src/drive/storage/native_types.rs`: the reader makes `.ora` something you can *open*, which is a different decision from what a Drive file holds, and nothing so far has required the second one. A vector or text layer is rasterised on the way out, since the format has no vector layer, and the whole document rides along verbatim in `META-INF/neutrino/document.json` so a Neutrino round trip loses nothing while every other reader ignores the file and still sees the right picture. That is the redesign's central rule — every advanced feature gets a Neutrino description *and* a rendered fallback — and it is why a masked layer's PNG has the mask baked into its alpha while the channel is *also* written separately. `writeOra` takes an injected `OraRenderer` rather than touching a canvas, which is what lets the package's structure be tested in jsdom, where `getContext('2d')` returns null.

**Reading has two paths that meet at one document.** A package this app wrote is rebuilt from the manifest — vectors come back as vectors, text as text, masks as masks — and one from Krita, GIMP or anything else is rebuilt from `stack.xml`, where every layer is necessarily raster. The manifest is validated through `parseDocument` rather than trusted, because a `.ora` is a file from outside and `META-INF/neutrino/document.json` is a name anybody can write; a damaged one falls through to `stack.xml` so the file still opens as flat layers. **Unknown extensions are ignored, not preserved** — OpenRaster's extension mechanism is bare attributes with no namespace, so there is no way to tell an extension from a typo and re-emitting one later could describe the file wrongly. Layer sizes come from each PNG's IHDR rather than from decoding the image: a forty-layer package would otherwise cost seconds before anything appeared, and `Image` does not exist in jsdom.

**A brush is a tool, not content.** `editor/paint/` splits into `brush.ts` (parameters), `stroke.ts` (pointer events → stamps, pure arithmetic) and `session.ts` (the only part that touches a canvas), so everything the real bugs live in is testable without a rendering context. Settings live in `localStorage` under `neutrino:drawing:brush`, never in the document — storing them in the file would make opening somebody else's drawing change your brush. Two rules are load-bearing: **a stroke's opacity applies to the stroke, not to each dab**, so a session paints into its own buffer and composites it once (otherwise every self-crossing comes out darker than the opacity asked for), and **stamp spacing carries across pointer events**, or a fast stroke is a row of dots at the positions the pointer happened to report. A paint tool with no raster layer to paint into creates one when it is armed rather than on the first stroke, because the stroke that made the layer would otherwise be the one stroke that drew nothing.

**Three of the brush's dimensions describe the material rather than the mark**, and they are what stops a stroke reading as a shape filled with a colour: `splatter` (`spray.ts`), `paper` (`paper.ts`) and `medium` (`medium.ts`). They sit beside `brush.ts` because each is arithmetic over numbers and colours and only the *applying* of it needs pixels — the same split the module already had. Every brush carries all three, so the engine never branches on the brush type; the inspector shows each control for the one tool it means something to (splatter for the airbrush, paper for the pencil, medium for the brush), which is a judgement about tools and therefore lives in `BrushPanel`, not in the engine. Unknown values are repaired in `clampBrush` rather than trusted, because a brush is restored from whatever JSON `localStorage` last held.

Where each one lands is the whole of what it means. **Splatter** replaces one dab with a scatter of droplets, per stamp, inside the stroke buffer — droplet *size* is chosen first and the count follows from it, since deriving size from a count makes a light splatter a handful of fat blobs instead of a finer nozzle. **The medium** decides a dab's colour, alpha and edge, then how the finished stroke meets the layer; its mixing is a **loaded bristle** (one `getImageData` of the layer per *stroke*, then a running colour that turns over at the medium's rate) rather than a per-dab sample, so oil carries a colour on and lets it go gradually, and the bristles start loaded with the brush's own paint or the first dab takes the layer's colour whole. A medium's `blend` overrides the Blend control where it has an opinion — a watercolour glaze is a multiply or it is not a glaze — and the control is disabled rather than hidden, since a setting that quietly stops applying is worse than one that says why. **Paper** masks the stroke once, anchored to the canvas rather than to the stroke: that is what makes a second pass find the same peaks the first one did, and is why the grain is periodic (`GRAIN_TILE`, procedural, seamless) and the pattern is phased by the layer's origin.

Two things about the grain are worth knowing before retuning it, because the obvious version of each is wrong and both were shipped that way first. **What makes a paper read as a surface is contrast, not depth.** The first version multiplied the noise through a weight-preserving curve so a rough sheet would not act as a brightness control, and the result was a gradient — a wash of light and dark, which is what a pencil looks like when it is *not* on paper. `bite` is the fix: it narrows a smoothstep window until the tooth is very nearly a threshold, so graphite reaches the peak or misses entirely, and the ragged edge that falls out of that is most of what makes the line look drawn. And **the tooth is a fixed size in canvas pixels, so a stroke narrower than it falls into the pits whole** — the shipping pencil at size 3 on rough paper drew almost nothing. `grainForSize` scales depth by how wide the brush is against the cell, which is also the real behaviour: a broad soft pencil rides the peaks, a fine point gets down into them.

Both of those masks are `destination-in`, which multiplies alpha, and `compositeStroke` runs on every preview frame as well as on the commit — so it composites from a **copy** of the stroke buffer. Applied in place a partial mask multiplies itself once per frame, and the stroke visibly dissolves at the selection's edge over a long drag. The copy is skipped entirely when there is no grain and no selection, which is the common case.

**A clipping mask is the one mask the compositor cannot resolve from the node alone** — it takes its shape from the nearest layer below that is not itself clipped, which is why `drawStackChildren` tracks a base across a whole run rather than pairing each layer with its predecessor, and why a hidden base hides its whole clipping group. The SVG writer says the same thing with `<mask style="mask-type:alpha">`, the only construction in that format meaning "the shape of what is underneath".

**A pixel selection is a region, stored as the shape it actually is.** `document/selection.ts` holds four kinds; `mask` is redesign §3's grayscale PNG and is what a flood fill, an invert or an imported file produces, while a rectangular marquee stays four numbers — rasterising one per mouse move would cost a full-canvas encode to store, less precisely, what the rectangle already says. Everything that consumes a selection goes through the same helpers, so the cheap kinds and the general one behave identically, and all four rasterise into `data/selection.png` on the way into a package.

**Paths carry cubic handles, and the compatibility trick is in the type.** `PathPoint extends Point`, so every polyline stored before handles existed parses and draws unchanged with no migration, and a point with no handles *is* a corner. Handles are **absolute**, which is what lets translate, scale and rotate map them with exactly the same arithmetic as the anchors — an offset-relative handle needs its own easily-forgotten case in each. Multi-contour paths (a `<path>` with a hole) put the extra contours in `subpaths` beside the first rather than in a uniform list, because almost every path has exactly one contour and a uniform field would have meant migrating all of them.

**SVG import (`io/svg/`) produces editable content, not a picture.** Lines, quadratics and arcs are all converted to cubics on the way in — each has an exact equivalent — so one segment kind has to be rendered, hit-tested, transformed, measured and written out instead of ten. A shape's own `transform` is folded into its geometry when it is a translate or axis-aligned scale and worn by a one-object layer when it rotates or shears, so a rotated rectangle stays a rectangle instead of becoming a four-point path. `<use>` imports as **instances of one symbol** rather than as copies, which is the same "stored once, referenced by UUID" the model has for reusable objects and is how the export writes it back. Nothing is fetched: an `<image>` with an external `href` is reported as skipped rather than followed, because a layer pointing at somebody's server breaks the moment the drawing is shared. Anything else it cannot represent is also reported rather than fatal — an SVG is usually somebody's whole artwork, and losing a gradient beats losing the drawing.

**Text on a path is a reference, never private geometry.** `TextLayerNode.textPath` names an ordinary `PathObject` that stays selectable and editable on its own terms; reshape it and the caption re-flows. That is exactly what `<textPath href="#id">` expresses, so the vector export needs no extension — and where the target is hidden and would not otherwise appear in the file, the curve is written into `<defs>` under the same id, because a `<textPath>` pointing at nothing renders as nothing. An earlier version of the app had the other design (a text shape carrying its own hand-placed cubics); it was unreachable by every other tool and had no SVG equivalent, and it is not the thing to reinstate.

**An adjustment layer is parameters, not pixels, and it corrects the layers below it inside its own stack.** `document/adjustments.ts` reduces all eight kinds the redesign lists to one of two operations — a per-channel **LUT** or a 4×5 **colour matrix** — and that reduction is the whole design: `render/colorOps.ts` implements two things per emitter (the canvas applies them to an `ImageData`, the SVG exporter writes `feComponentTransfer` or `feColorMatrix`) rather than eight that can drift apart one at a time, and the mapping to SVG is exact rather than approximate. `color-interpolation-filters="sRGB"` goes on every filter the exporter writes, because SVG filters are linearRGB by default and a tone curve applied in the wrong space is visibly different while looking like rounding. The correction stops at the group boundary — Photoshop's "pass through" reaches out of the group and this deliberately does not, because a group is then the thing that bounds a correction and there is nowhere else to put that control. `opacity` is the strength, `mask` confines it (a `clipping` mask to the alpha of the layer below), `visible` turns it off, and `blendMode` means nothing for a layer with no pixels, so the panel offers none. Two things follow: **a partial correction is a mix, not a fade** (half a hue rotation is a different colour, so the corrected pixels are blended back towards the originals per pixel — and the SVG export says the same thing by drawing the original with a filtered copy over it at the layer's opacity), and **the stack composites into a buffer it owns**, since reading the target instead would let a correction at the root grab the editor's page shadow and the grey around it.

**A filter is a property of a layer**, ordered, and applied *before* the layer's mask: a masked blur is a blur inside a shape, while masking first smears the mask's own edge. The rendered fallback costs nothing — the OpenRaster writer rasterises every layer through the same compositor, so `data/layer-*.png` *is* the filtered result — which is why the manifest's `filters` entry names that PNG while an adjustment's names `mergedimage.png`. Pixelate and noise have no SVG equivalent (the format has no block average, and `feTurbulence` is Perlin noise rather than per-pixel grain), so they are dropped from an `.svg` and reported rather than approximated into a different picture under the same name. The blur's `radius` is the **standard deviation**, the quantity CSS's `blur()` and SVG's `stdDeviation` take. It shipped wrong once and the bug is worth knowing: one ideal box width floored to the nearest odd integer is 1 for anything below about σ = 1.5, a box of width 1 is the identity, and so every small blur silently did nothing — which looks exactly like a filter that has not been switched on. `boxSizes` spends the remainder across the three passes instead.

**Colour management is honest about an 8-bit pipeline.** Wide gamut is real: `surfaceFactoryFor` asks for a `display-p3` context so every buffer the compositor allocates is wide-gamut, with the support probe answered once per page rather than per frame. An embedded ICC profile goes into a package **twice** — as `META-INF/neutrino/color.icc` and as an `iCCP` chunk inside `mergedimage.png`, because an image viewer looks in the file and not in a directory beside it; `io/png/chunks.ts` is the pure half (framing, CRC, splice after IHDR) and `io/png/deflate.ts` the one step that needs `CompressionStream`, where a browser without it skips the chunk rather than failing the export. A profile is validated through `io/icc.ts` before it is stored, since bytes that are not a profile make an `iCCP` chunk strict decoders refuse — the picture lost to a metadata error. **16-bit is read, not written**: a canvas is 8 bits per channel, so writing a 16-bit PNG would pad rather than preserve, and what the model does instead is record the depth an import arrived with (`pngBitDepth`, off the IHDR — the last moment it exists) and show it. **HDR is a description plus an SDR preview**, exactly as the redesign specifies, with the manifest naming `mergedimage.png` as that preview; nothing tone-maps an SDR render into a dimmer SDR render to look busy.

**A linked asset is provenance, not a second copy of the image.** The redesign asks for an embedded fallback copy and the layer's own pixels *are* it — already in the document, already written to `data/layer-*.png` — so storing them again on the asset would put the same megabytes in the file three times to say what it can already demonstrate. An asset is the URI, a content hash (FNV-1a: it identifies, it does not authenticate), the size it had on import and when; `RasterLayerNode.assetId` points back, a fetchable source gets a Reload action, and assets whose layer is gone are pruned on save. A `data:` URI is never stored as the source — it *is* the image, and keeping it would be the duplication the design avoids.

**Workspace state is not image content, and the test for that is literal**: `documentToSvg` of a rotated, ruled, guided document is byte-identical to the plain one. `document/workspace.ts` holds rulers, units, guide visibility and locking, snapping, canvas rotation and what was open, and it all rides in `META-INF/neutrino/document.json`. **The grid stayed where it was** — spacing, origin and its own snap flag are geometry a drawing is built against and predate this, and moving them would have meant migrating every drawing already saved to say the same thing elsewhere; snapping tries the grid first and the other candidates only where the grid did not move the value, or a guide two pixels off a grid line fights it and the winner depends on the order of two `if`s. **Canvas rotation is what forced the viewport to become a matrix**: a rotated view means a screen point no longer maps back by subtracting and dividing, so the pointer, the text overlay and the ruler ticks all go through `viewportMatrix` and its inverse. It is a view setting — nothing in the document moves and exports are unaffected. **The rulers overlay the canvas rather than insetting it**, so turning them on does not move the drawing and a guide dragged out of one lands where the pointer is; `rulerTicks` picks steps from the 1-2-5 series so a labelled tick is never closer than 64 screen pixels, which keeps a ruler readable at 8% and at 1600% with no special case. A guide dragged off the page is deleted, which also settles what happens to one released before it reaches the page: it is never created. And **viewport, tool and selection are folded in at save time, not at edit time** — panning or arming a different tool would otherwise be a document change, and a document change is an undo step, so ⌘Z would scroll the page instead of undoing the last stroke.

**The document version stays 2 across all of this.** Every field phases 3–8 added is optional or a widening of one that already existed, so a body written before them opens under this reader and a body written here opens in the earlier build with the new features dropped rather than the file refused. The adjustment layer is the one addition that is a new node *type*, and an older build's `parseDocument` drops a node it does not recognise — so such a drawing opens there missing a correction and keeping everything else, which is the same trade every optional field makes. Bumping the number would have bought nothing and cost every drawing already saved.

Two smaller things worth knowing. A drawing is created as a **zero-byte file** — the server writes no seed, because a constant one would give every drawing in the system the same layer UUIDs and would sit in storage in the clear until the first save — so the editor writes the first body itself, encrypted, exactly as the OOXML editors do. And `extractDrawingText` indexes layer and group **names** as well as text-layer content, because a drawing is often all shapes and no prose: without the names a flowchart is unfindable by anything but its title.

**Sheets editor** — `apps/web/src/app/(apps)/sheets/editor/`. Key architecture:
- `SheetEditor.tsx` — top-level component owning all state (currentCell, selectionAnchor/selectionActive, data Map, colWidths/rowHeights). Keyboard shortcuts are registered via `document.addEventListener('keydown', ...)` in `useEffect` with empty deps; handlers read state from stable refs updated every render, so the effect never needs to be re-registered.
- `SheetGrid.tsx` — virtualised grid (prefix-sum viewport culling). Selection overlay is an absolutely-positioned `div` with an inline border, not a CSS class. Cell elements have `id={cellId}` for direct DOM access.
- `Cell.tsx` — pure presentational; `.cell` has hardcoded `background-color: #ffffff` and `color: #000000` that must never be overridden by theme CSS (user cell fill colours applied via inline `cellStyle`). `.cellSelected` adds a tinted overlay on top.
- Hooks under `hooks/`: `useCellEditing`, `useHistory`, `useClipboard`, `useSheets`, `usePersistence`, `useExport`. `useCellEditing` owns formula bar state, formula pick mode, style application, and merge/unmerge.
- Cell IDs are spreadsheet addresses: `A1`, `B3`, `AA10`. `alphaToNum`/`numToAlpha` in `utils.ts` convert between column letters and 1-based integers.
- **Header selection** — `headerSelection.ts` is the pure model behind selecting one or more row/column headers (plain click, Cmd/Ctrl+click to toggle, Shift+click or drag to extend; a click on the other axis starts over). `SheetGrid` selects on **mousedown**, not click — a click only lands after mouseup, by which time a drag is over — and reports the modifier state up; `SheetEditor` holds the resulting `HeaderSelection` and mirrors its *bounding* range onto `selectionAnchor`/`selectionActive` so the name box, presence and arrow keys keep working. The bounding box is not the selection: Cmd+click leaves gaps, so `selectedCells`, the header context menu (which deletes/inserts/clears/hides every selected header in one undo step) and `applyStyleToSelection` all read the exact set instead. Materialising it is the expensive part — a column is `MAX_ROWS` ids — so it is `useDeferredValue`d and the grid paints its highlight from the header *indices*, never from the cell set. Any other path that moves the selection (undo, Select all, Find) drops the header selection via the anchor/active mismatch effect rather than each caller remembering to clear it.
- Dark mode: the app root sets `data-theme="dark"`. CSS Modules require `:global([data-theme="dark"]) .localClass` to target ancestor-attribute dark overrides within a module file. The grid header and cell backgrounds are hardcoded light colours intentionally — do not add dark-mode overrides for them.
